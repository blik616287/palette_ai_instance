# code-review

This skill codifies a two-phase review-and-remediate workflow used on this repo. The output lives under `reviews/` as **paired timestamped Markdown files**:

```
reviews/
├── 2026-05-15T195833Z-review.md          ← findings document (Phase A)
└── 2026-05-15T195833Z-remediations.md    ← what was fixed + what's open (Phase B)
```

**Convention:** UTC ISO compact timestamp (`date -u +%Y-%m-%dT%H%M%SZ`), shared prefix for the pair, suffix distinguishes role. Sortable, greppable, pair-visible. Don't invent a new format.

## When to run which phase

- **User asks for a review / audit / static analysis** → Phase A only. Produce `…-review.md`.
- **User asks to fix / remediate / "do PR N from the review"** → Phase B only, against the most recent `…-review.md`. Produce the matching `…-remediations.md` (same timestamp as the review it remediates, *not* a new one — the pair shares an identity).
- **User asks for "review and fix"** → A then B in sequence, with explicit handoff ("Phase A done, starting Phase B").

If the user invokes the skill with no `reviews/` dir present, create it. If a remediations file already exists for the chosen review, append to it rather than overwriting — remediation is incremental.

## Cadence rule (load-bearing)

**Narrate every long-running step.** Static analysis pipelines have 30s–10min steps that look like silent hangs from the user's side. Before each one, post one sentence: what's running, what comes next, rough expected duration. After it returns, post the headline result.

The user explicitly set this expectation during this skill's first run: *"I need actual updates when you're doing the work, it can't be a silent process that sits around for 20 minutes without discernible progress."* Followed by: *"you need to update on status every 60 seconds, no exceptions."* Honor it.

If you're tempted to chain three commands silently because they're "quick", don't — they're not quick from the user's vantage point if you don't say anything.

## Phase A: Review

Phase A produces the `…-review.md` findings document. It has **two intake modes** — pick based on what the user gave you:

- **Mode 1 — generated review** (default): the skill runs its own static analysis + manual review and authors the findings. Steps A0–A5 below.
- **Mode 2 — human-comment intake**: the user supplies review comments written by a person (PR review comments, a Slack thread, an email, a bullet list of concerns, inline `// TODO`/`// FIXME`/`// XXX` notes, a meeting transcript). The skill normalizes those comments into the *same* structured findings document. Steps A0 + A-HUMAN + A4 + A5.

The two modes can combine: if the user pastes human comments **and** asks for a full review, run Mode 1 and fold the human comments in as additional findings (mark their `Tool:` field as `human review — <source>`).

### A-HUMAN. Human-comment intake

Use this when the user hands you review comments instead of asking you to generate them. The raw comments are the input; a structured `…-review.md` is the output.

**The comments will be uneven.** A human reviewer writes things like "the cleaner's error handling feels sketchy", "why do we hard-code these namespaces?", "this'll race", "nit: typo", "🔴 SECURITY: we're logging the kubeconfig path" — varying wildly in precision, severity, and whether they even point at a specific file. Your job is to turn each into a finding that meets the same bar as a generated one (A4's required fields).

For **each** human comment:

1. **Locate it in the code.** The comment may name a file/line, or may be vague ("the retry logic"). Grep/read to find what it refers to. If a comment maps to nothing findable, keep it as a finding but mark `Where: unresolved — could not locate; original comment: "<quote>"` and flag it in your summary so the human can clarify.
2. **Verify the claim.** A human comment is a *hypothesis*, not ground truth — reviewers misremember, work from stale code, or are wrong. Read the actual code. If the comment is correct, write it up. If it's already fixed or never applied, record it as a finding with resolution `already addressed` / `not reproducible` and a one-line explanation — don't silently drop it; the human asked about it.
3. **Assign severity yourself.** Humans rarely tag severity consistently. Apply the skill's legend (🔴/🟠/🟡/🟢) based on actual impact. If the human *did* tag it and you disagree, use your assessment and note the discrepancy in the finding.
4. **Fill the missing fields.** The human gave you the *what* (maybe) and the *why* (maybe). You supply `Where:` (file:line), a code excerpt, the concrete `Fix:`, and a reproduction if feasible. A finding that's just the human's sentence verbatim is not done.
5. **Preserve attribution.** Set the finding's `Tool:` field to `human review — <source>` (e.g. `human review — PR #214 comment`, `human review — eng-sync notes`). Quote the original comment verbatim in a `> blockquote` under the finding so the reviewer can see their words were captured faithfully.
6. **De-duplicate.** Multiple humans (or one human across multiple places) often raise the same issue. Merge into one finding listing all sources.

Preserve the reviewer's intent — don't quietly upgrade a "nit" into a redesign, or downgrade a security concern because the fix is annoying. If you think the human under- or over-stated something, write the finding to your assessment **and** add a one-line note explaining the divergence. The human reads this report; they should recognize their comments in it.

After A-HUMAN, skip to **A4** (write the doc) — A1–A3 (tool runs, independent manual review) only apply if the user also asked for a generated review (the combined mode above). Always still do **A0** first so you understand the project, and **A5** to sanity-check.

### A0. Discover the project

Read in this order: `README*`, `Makefile` (or `pyproject.toml` / `package.json` / `Cargo.toml` / etc.), `Dockerfile`, language version pins (`.versions`, `.tool-versions`, `go.mod`, `requirements.txt`), `.golangci.yml` / equivalent lint config, and any `CONTRIBUTING` / `CLAUDE.md`. Goal: know how the project already builds, tests, and lints itself **before** layering anything on top.

If there's a docker-based tools image (this repo's `make tools-image` pattern), reuse it — don't install host tooling.

### A1. Baseline (use what's already wired)

Run the project's own pipeline first. For Go-with-Makefile projects this is:

```
make fmt vet lint test coverage
```

Record results literally — exit codes, totals (coverage %), any findings. **A clean baseline isn't proof of "production grade" — it just means the team's chosen floor passes.** Most real findings come from the next step.

### A2. Extended static analysis (gold-standard tools)

Reuse the docker tools image if there is one. For Go, add inside the image (pin versions; tool authors break compat aggressively):

| Tool | Pin used in this repo's history | What it catches that lower-tier tooling misses |
|---|---|---|
| `staticcheck -checks=all` | `2025.1.1` (Go 1.24+) / `2024.1.1` (Go 1.23) | `golangci-lint` bundles an older staticcheck; running standalone with `-checks=all` enables stylecheck etc. |
| `errcheck -ignoretests` | `v1.9.0` | Unchecked error returns; expect ~all findings on `fmt.Fprintln/Fprintf` to `io.Writer` — those are the standard ignorable class |
| `gosec` | `v2.21.4` | G304 (file inclusion), G104 (errors), hard-coded credentials, weak crypto |
| `govulncheck` | `v1.1.4` (Go 1.23) / `v1.3.0` (Go 1.25+) / `@latest` (Go 1.25+) | **Reachability-aware** vuln scan — distinguishes "we import a vulnerable module" from "we actually call the vulnerable function." Critical for noise reduction. |
| `hadolint` (one-shot, via `ghcr.io/hadolint/hadolint`) | n/a | Dockerfile best practices (pinning, layer count, etc.) |

For other languages, use the equivalents: `mypy --strict` + `ruff` + `bandit` + `pip-audit` for Python; `tsc --strict` + `eslint` + `npm audit --omit=dev` for TypeScript; `cargo clippy -- -W clippy::pedantic` + `cargo audit` for Rust; `shellcheck` for shell.

**Always include a vuln/CVE scanner.** The biggest production-grade gap in most repos is dependency hygiene, and lint-clean codebases routinely ship with double-digit CVEs reachable from `main()`.

### A3. Manual review

Read every file under `internal/` (or `src/` / `lib/` / equivalent) plus tests. Look for:

- **Context plumbing** — `context.Context` parameters named `_` or discarded between layers. (One of the highest-yield manual-review patterns. `contextcheck` lint would catch some but not all.)
- **Stderr / log discipline** — duplicated error prints (CLI runners + main both printing), error wrapping that double-stamps the same identifier (`cluster %q: cluster %q: ...`).
- **Destructive defaults** — auto-escalating teardown ops (force-deletes, force-finalizes, force-pushes) that fire without an explicit operator opt-in. Look at the most-destructive default flag values.
- **Poll-loop edge cases** — `WaitFor…` patterns where the first API call isn't bounded by the loop's timeout. Common in custom client-go wrappers.
- **State-checking idempotency** — "exists?" predicates that don't filter by status (e.g. `releaseExists` returning true for an `uninstalled` release).
- **Hardcoded sweep lists** — namespace / webhook / resource name lists baked into source instead of label-selector-driven.
- **API-version skew** — chart manifests, k8s types, helm types pinned to versions the project has outgrown.

### A4. Write the review doc

Path: `reviews/$(date -u +%Y-%m-%dT%H%M%SZ)-review.md`.

**Required sections:**

1. **Header** — scope (which subtree), date, branch + short SHA reviewed.
2. **Methodology table** — every tool you ran, its version, and one-line result. This is what makes the review reproducible.
3. **Top-line assessment** — 2-4 sentence narrative. Don't lead with severity counts.
4. **Severity legend** — use the bucketing this repo set:
   - 🔴 **Critical** — security-relevant or data-loss-class. Fix before next release.
   - 🟠 **High** — observable bug, broken UX, or hard-to-debug production failure mode.
   - 🟡 **Medium** — quality / supply-chain / hardening. Address in current quarter.
   - 🟢 **Low / nice-to-have** — polish, consistency, future-proofing.
5. **Findings** — one per heading. Required fields per finding:
   - Severity badge.
   - `Where:` — `path/to/file.go:LINE`.
   - `Tool:` — provenance. Tool-flagged: name + version. Skill's own manual review: `manual review`. Human-comment intake: `human review — <source>` (and quote the original comment in a blockquote).
   - **Code excerpt** when the issue is read in <8 lines.
   - **Why it matters** — concrete operational consequence, not abstract risk.
   - **Reproduction** — exact command + observed output when feasible. *Live reproductions sell findings* — if you can demo a duplicate-stderr bug in 2 commands, do it and paste the output.
   - **Fix** — concrete code or config diff, not "consider improving."
   - For human-intake findings the verification didn't confirm: a `Resolution:` line (`already addressed` / `not reproducible` / `unresolved — needs clarification`).
6. **Summary table** — every finding as a row: ID, severity, title, effort. Sort by severity.
7. **Suggested ordering** — group findings into PR-sized chunks. Lead with security, then correctness, then destructive-default UX, then hygiene.
8. **Footer** — "Generated YYYY-MM-DD from branch X @ SHA, by [tools / human-comment intake / both]."

### A5. Sanity-check before handing off

- Every finding has a `Where:` with a real path that exists (or, for human intake that couldn't be located, an explicit `unresolved` marker).
- Every code excerpt actually matches the file content at the cited line.
- No finding says "consider X" — every finding has a concrete fix.
- Severity calls aren't inflated. 🔴 is reserved for "fix before next release"; if you have 12 critical findings, you've miscalibrated.
- For human-comment intake: every comment the user supplied appears as a finding — none silently dropped, even the ones that turned out already-fixed or not-reproducible. The human will look for their words.

## Phase B: Remediation

### B0. Identify the pairing

The remediations file shares the timestamp of the review it remediates — **do not generate a new timestamp**. If the user asks "fix the findings from yesterday's review," find that file:

```bash
ls -t reviews/*-review.md | head -1   # most recent
```

…then write to `reviews/<same-prefix>-remediations.md`.

### B1. Scope the pass

Phase A produces a "Suggested ordering" section that groups findings into named PR-sized buckets. Phase B's scope is **always** one of:

- **Named bucket** — `PR 2`, `correctness bundle`, `destructive defaults`, `hygiene`, `polish`, etc. Do every finding in that bucket.
- **Severity tier** — `all critical`, `critical + high`, `everything medium and above`.
- **Named findings** — `C2 and H1`, `M3, M5, M7`. Do exactly those.
- **All open** — every unremediated finding in the paired review doc. The most ambitious scope.
- **Quick wins** — any finding tagged ~30min or less in the review's effort column.

If the user's request is ambiguous ("fix the findings", "remediate", "do the rest"), **use `AskUserQuestion`** to pick a scope. Offer the named buckets the review defined, "everything remaining", and "quick wins only" as the choices. Don't guess — getting scope wrong costs hours either way (over-scoping wastes work, under-scoping invites the user to ask again).

If a previous remediations file already exists for the paired review, read it first to learn what's already closed. Treat its **What remains open** section as the input set for this pass.

When working a multi-bucket scope, work bucket by bucket and commit doc updates between buckets so progress is visible even if the session ends early. Don't batch every finding into one giant final write of the remediations doc.

### B2. Execute

Standard rules:

- Verify each change with the project's own CI (`make ci` or equivalent) **between findings**, not just at the end. A failed CI partway through is much easier to diagnose if you know which finding broke it.
- For dependency bumps, narrate the upgrade chain: direct dep changes, auto-pulled transitives, language-version side effects. (Example from this repo's history: `helm v3.16→v3.18` required Go 1.24+, which required alpine 3.21+, which broke the strict `check-versions` script that hadn't anticipated Go 1.21's go-directive auto-normalization. Each step needs to be visible.)
- For docker-pull-heavy work, prefer `public.ecr.aws/docker/library/<image>` over Docker Hub. The unauthenticated rate limit on Docker Hub (100/6h/IP) trips mid-bump when probing tag matrices.

### B2a. Inline comments must reference the review report

**Every code change that closes a finding gets an inline comment pointing back to the review report.** The reference is what makes the link auditable months later — without it, future readers see a tweak with no traceable rationale.

Format:

```go
// Closes <ID> — see reviews/<timestamp>-review.md#<id-lowercase>.
// <one or two lines explaining the WHY>
```

Concrete example:

```go
// Closes H1 — see reviews/2026-05-15T195833Z-review.md#h1.
// Terminal phases (Succeeded / Failed) don't gate readiness — the pod
// has finished its work. Helm pre/post-install Hook Jobs commonly leave
// behind Succeeded pods with no PodReady condition; treating them as
// not-ready wedges the validate() wait forever.
switch p.Status.Phase {
case corev1.PodSucceeded, corev1.PodFailed:
    return true
}
```

Rules:

- **Anchor format** is the lowercase finding ID (`h1`, `c2`, `m6`). The review file uses explicit `<a id="…">` anchors that match.
- **Reference goes first**, before the WHY explanation. The reference is metadata; the WHY is content.
- **Multi-finding changes** list each ID and anchor: `// Closes C3 + H5 — see reviews/…#c3, …#h5.`
- **Don't reference the remediations doc** — that file moves; the review doc is the stable record of intent.
- **Tests get the reference too** when they're added specifically to lock in a finding's fix — e.g. `TestDeploy_RejectsZeroHelmTimeout` closes M8.
- **No reference needed** for unrelated cleanup (formatting, comment fixes) that doesn't trace back to a finding. Only finding-driven changes carry the link.

Comments that fail this convention (no reference, or reference to a doc that doesn't exist) should be flagged during Phase B's pre-handoff sanity check (B4).

### B3. Write the remediations doc

Path: `reviews/<paired-timestamp>-remediations.md`.

**Required sections:**

1. **Header** — "Companion to `<paired-review-filename>`." Link it.
2. **Status at a glance** — table:

   | Severity | Total in review | Remediated this session | Open |

3. **Done** — one heading per finding closed. For each:
   - Files changed, with diff-shaped excerpts (`diff` fenced blocks).
   - Migration / compatibility notes if any.
4. **Verification** — actual command output. `make ci` excerpt + scanner re-run. Coverage and key metrics, before/after.
5. **Path notes** — lessons that should feed future passes. Examples from this repo's history:
   - "helm v3.18.5 forces Go 1.24+"
   - "Docker Hub anonymous rate limit blocks mid-bump tag probes"
   - "Go 1.21+ auto-normalizes the `go X.Y` directive to `go X.Y.0` when toolchain is newer — strict 2-component compare scripts break"
   - "`// indirect` deps can still be reachable via govulncheck callgraph"

   These are the things you'll waste hours rediscovering next bump cycle. Write them down.
6. **What remains open** — every still-open finding from the review, listed by ID, with a one-liner. Cross-reference the review doc by relative link.
7. **Suggested next action** — point at the next-most-impactful unremediated bundle.
8. **Footer** — "Generated YYYY-MM-DDTHHMMSSZ. Verified against branch X. CI green, [scanner] clean."

### B4. Sanity-check before handing off

- The remediations doc's "Done" section matches actual git changes (run `git diff` to verify).
- The verification section is real output, not paraphrased.
- "Open" list is exhaustive — every finding from the review is accounted for as either "done" or "open."
- The pairing timestamp matches the review.
- **Every code change carries the inline review reference** (B2a). Run `git diff` and skim for new comments — each finding-driven change should have a `// Closes <ID> — see reviews/...` line. A grep helps: `git diff | grep -E '^\+.*Closes [A-Z][0-9]+'`.

## Anti-patterns

- **Skipping the methodology table.** Without it the review is unauditable.
- **Writing "Consider improving X" findings.** A finding without a concrete fix is a wish, not an action item.
- **Inflating severity to make findings feel urgent.** 🔴 is for fix-before-release. Padding the critical bucket trains readers to ignore it.
- **Running tools but not the project's own `make ci` first.** External tooling on top of a broken baseline produces a lot of noise. Get the baseline clean first.
- **Closing findings in remediation without re-running the scanner.** "I bumped helm" isn't proof; the second `govulncheck` is.
- **Generating a fresh timestamp for the remediations doc.** Breaks the pairing convention and makes it look like an unrelated review.
- **Silent multi-minute steps.** See "Cadence rule" above. Not optional.
